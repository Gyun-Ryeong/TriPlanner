# TriPlanner - 대화형 여행 플래너 (RAG)

대화로 여행 정보를 모으고, **날씨·미세먼지·최신 이슈 뉴스**를 반영해서 일자별 여행 일정을 짜주는 챗봇입니다.
일정이 나온 뒤에도 "2일차는 실내로 바꿔줘" 같은 말로 계속 수정할 수 있어요.

## 동작 흐름

```
사용자 ↔ 챗봇 (같은 session_id로 이어지는 대화)
 │
 ├─ 정보 수집 대화: 지역 → 출발일 → 기간 → [한 번만] 동행·취향을 하나씩 되묻기      travel/chat.py
 │     지역/날짜는 규칙 파서가 우선(내일, 이번 주말, 2박 3일 ...), 동행/취향은 LLM       travel/dates.py, regions.py
 │
 ├─ 정보가 모이면 외부 데이터를 병렬 수집 (같은 여행 조건에서는 재사용)                 travel/context.py
 │     ① TourAPI 관광지·문화시설·레포츠·축제    ② 네이버 뉴스(특보/취소/통제)
 │     ③ 기상청 단기예보(오늘~3일)            ④ 에어코리아 미세먼지(오늘~모레 예보 + 실시간)
 │
 ├─ 일자별 컨디션 계산: 비/눈, 폭염·한파, 미세먼지·초미세먼지 '나쁨' → "실내 위주"     travel/conditions.py
 ├─ 후보를 임베딩 검색(취향 유사도) + 궂은 날용 실내 후보 보장 → 소개글 보강             travel/context.py
 ├─ LLM이 일자별 일정을 JSON으로 생성 (후보 id로만 장소 지정)                        travel/planner.py
 ├─ 검증: 없는 장소·중복 제거, 날짜 맞추기 / 실패 시 규칙 기반 기본 일정으로 대체
 └─ 답변 렌더링: 날씨·미세먼지 수치는 코드가 직접 채움, 궂은 날 실외 일정이 많으면 경고

일정이 나온 뒤: "2일차는 실내로 바꿔줘", "맛집도 넣어줘", "제주로 바꿔줘" → 수정/재생성
               (외부 API는 다시 부르지 않고 이미 모은 데이터를 재사용)
```

**설계 포인트**
- **날씨·미세먼지 판단은 코드가 합니다.** LLM은 "실내 위주" 같은 결론과 수치를 프롬프트로 받기만 하고, 화면의 수치도 코드가 직접 채워서 지어낼 수 없습니다.
- 장소는 `C1`, `C2` 같은 **후보 id로만** 지정하게 하고 서버가 실제 정보로 되돌립니다. 후보에 없는 장소는 버립니다.
- **LLM이 죽어도 대화가 이어집니다.** 정보 추출은 규칙으로, 일정은 날씨를 반영한 기본 배치로 대체하고 제약사항에 사유를 남깁니다.
- 일정이 나온 뒤에는 "내일 비 와요?" 같은 질문으로 출발일이 바뀌지 않도록, **변경 의도가 있을 때만** 지역·날짜를 바꿉니다.
- 후보 소개글(detailCommon2)은 일정에 쓸 후보에만 조회하고 파일로 캐시합니다 (호출 수 절약).
- 시도 코드는 하드코딩하지 않고 `ldongCode2`에서 이름으로 찾습니다 (행정구역 통합 대비). 실패하면 기본 코드, 그것도 비면 구 `areaCode`로 재시도합니다.

## 답변 하단 서식과 내부 정보

- **모든 답변의 맨 끝**에는 고정 문구 `🛠 개발자 정보 (제약사항·한계)`(TourAPI 4.0 기반, 날씨·미세먼지는 기상청 단기예보 기준, 실내/실외는 추정, 운영시간은 사전 확인 권장)가 붙습니다. (첫 인사말에는 붙지 않아요) 이 문구는 항상 같은 정적 문구이고 AI 대화 기록에는 섞이지 않습니다.
- 이것과 별개로 **실제 API 오류·소요 시간 같은 동적 내부 정보는 사용자에게 나오지 않습니다.** (`caveats`·`timings`는 비워서 내려가고 화면의 디버그 옵션도 없음)
- 사용자가 "개발자 정보", "시스템 정보", "제약사항", "프롬프트" 등을 물어도 내부 내용 없이 `본 서비스는 한국관광공사 TourAPI 및 최신 위치 데이터를 활용하여 맞춤형 여행 정보와 일정을 제공하는 AI 가이드입니다.`로만 답합니다(역시 하단 서식 포함).
- 개발·점검할 때만 `.env`에 `DEV_MODE=on` (`check_setup.py`는 자동으로 켜서 실행). 서비스에서는 꺼두세요.

### 디버그 정보(API 오류·소요 시간) 보는 방법

1. `.env`에 `DEV_MODE=on` 추가 후 저장 → Streamlit을 껐다가(`Ctrl+C`) 다시 실행 (`.env`는 시작할 때만 읽어요)
2. 화면 왼쪽 사이드바에 **"🛠 개발 모드가 켜져 있어요"** 와 **"디버그 정보 표시"** 체크박스가 생김 → 체크
3. 답변 아래에 **"🧪 디버그 정보 (개발 모드)"** 접이식 영역이 나타나고 API 실패 사유, 단계별 소요 시간, AI 속도가 보입니다.
   (사이드바가 안 보이면 화면 왼쪽 위 `>` 화살표로 펼치세요)
- API는 `DEV_MODE=on`일 때만 `/chat` 응답에 `caveats`, `timings`, `llm_stats`를 포함합니다.
- 오른쪽 위 `Deploy` 버튼과 개발자 메뉴는 `.streamlit/config.toml`의 `toolbarMode = "minimal"`로 숨겼어요.

## 여러 지역·전국 지원

- **다중 지역 일정**: "대구 1박2일, 부산 2박3일 짜줘"는 지역별로 **독립된 일정**을 각각 만듭니다. 출발일을 한 번만 묻고(말했으면 바로), 지역은 순서대로 이어서 배정해요(다음 지역은 이전 일정 다음 날부터). 이후 "부산 2일차는 실내로 바꿔줘"처럼 지역을 말하면 그 지역 일정만 고치고, 지역 없이 말하면 어느 지역인지 되묻습니다.
- **새 지역을 말하면 이전 지역 데이터는 초기화**됩니다. (성남 일정이 있어도 "부산 2박3일 일정 짜줘"는 부산 일정을 새로 만들고, 이전 세부 지역(성남)이 남지 않음. 지역 이름 없는 질문 "2일차는 실내로 바꿔줘"는 기존 일정을 고침)
- **목록·소식 요청**도 여러 지역을 말하면 지역별로 나눠 답합니다 ("대구, 부산 맛집 알려줘").
- **전국 기초지자체**: 도시 목록에 없는 시·군·구(곡성, 영월, 울진 ...)는 TourAPI 법정동 시군구 목록(`ldongCode2`)으로 만든 사전(`cache/gazetteer.json`, 30일)으로 찾습니다. 일상 단어와 겹치는 이름(고양이/고양, 화성 등)은 "고양시"처럼 시·군·구를 붙여야 인식하고, "고성"처럼 시도마다 있는 이름은 시도를 함께 말해야 해요.

## 요청 유형별 응답

| 요청 | 예 | 응답 |
|---|---|---|
| **특정 장소 문의** | "분당 한우마을 정보 알려줘", "XX공원 어떤 곳이야?", "모란시장 영업시간" | **그 장소 하나만**: 📍도로명 주소 · 🕒영업/관람 정보 · 💡주요 특징. 다른 곳을 추천하지 않고, 못 찾으면 이름을 다시 물어봅니다 (추천 요청과 구분: "추천해줘"가 없고 장소 이름이 들어 있을 때) |
| **숙박 / 축제·행사 / 추천 여행코스** | "성남 숙소 추천해줘", "부산 축제 알려줘", "성남 추천 여행코스 알려줘" | 각각 3~5곳 목록. 숙박: 📍위치·🕒체크인/아웃·💡특징 / 축제: 🗓기간·📍위치·💡특징 / 여행코스: 📍·⏱소요 시간·거리·💡특징 ("주말 데이트 코스 추천해줘"처럼 일정을 짜달라는 '코스'는 일정으로 처리) |
| **A. 여행지 추천** | "성남 여행지만 추천해줘", "실내 데이트 장소 알려줘" | 날짜를 묻지 않고 바로 **테마별 목록** (자연·공원 / 문화·역사 / 힐링·산책 / 쇼핑·실내 ...). 장소명 · 📍주소 · 💡특징 1~2줄(소개글에서 발췌) |
| **C. 맛집·카페** | "분당 맛집 알려줘", "판교 카페" | **3~5곳**: 📍위치 · 🍴대표 메뉴/특징 · 🚶접근성(주차·영업시간·휴무). 메뉴·영업 정보가 채워진 곳을 우선 |
| **B. 일정** | "성남 7일 일정 짜줘" | 시간대·이동·식사가 있는 일자별 일정 (아래) |

| **지역 소식 (뉴스)** | "성남시 요즘 소식 있어?" | **A. 포괄 질문**: 그 지역 최근 2주 소식 핵심 3~4개 (같은 사건은 하나로, 다른 지역 기사 제외) |
| | "성남 야외공연장 뉴스 알려줘", "모란시장 관련 소식" | **B. 특정 대상**: 그 대상이 직접 나오는 뉴스 **하나만** (최근 3개월, 지역을 말했으면 그 지역 기사만). 없으면 "직접 관련된 최근 소식은 찾지 못했어요" |

- 뉴스는 네이버 뉴스(HUB) 검색 결과의 제목·요약만 쓰고 AI는 쓰지 않아요(기사에 없는 내용을 지어내지 않고 빠름). 검색이 실패하면 "지금은 소식을 불러오지 못했어요"로만 안내하고 사유는 개발자 정보에 남깁니다.
- 일반 여행지 추천("가볼 만한 곳 추천해줘")에는 맛집·카페 카테고리(최대 3곳)도 함께 나오고, "여행지만 추천해줘"처럼 '~만'을 붙이면 빠집니다.
- 서론·인사 없이 제목부터 시작하고, 묻지 않은 내용(마무리 질문, 일정에 붙는 뉴스, 안내 문구)은 붙이지 않습니다.
- 맛집 목록의 메뉴·영업시간은 TourAPI `detailIntro2` 값입니다. 데이터에 없는 항목은 지어내지 않고 줄을 생략하거나 소개글로 대신해요(대표메뉴가 비는 가게는 취급메뉴 → 소개글 순으로 대체).
- 일정에서 "맛집 위주로 가고 싶어요"는 취향 답변으로, "근처 맛집 알려줘"는 목록 요청으로 구분합니다. 일정이 있는 중에 목록을 물어봐도 일정은 그대로 유지돼요.

## 일정 출력 형식

AI는 **날짜별로 방문할 장소와 순서**만 정하고, 나머지는 코드가 채웁니다 (지어낼 수 없게).

```
### 📅 1일차 · 10/7(수) — 컨셉
☀️ 맑음 · 11~23℃ · 강수확률 0%  |  😷 미세먼지 좋음 · 초미세먼지 좋음 (예보)
- **10:00 - 11:30** | **장소명** (관광지 · 🌳 실외) — 활동 설명
  - 📍 위치: 주소
- 🚶 11:30 - 11:45 | 이동: 장소A ➔ 식당B (도보 약 10분)
- **11:45 - 12:55** | 🍽️ **점심 식사: 식당명**
  - 📍 위치: 주소
```
- 장소 이름·주소는 TourAPI 데이터 그대로, **시각은 유형별 체류 시간**(관광지 90분, 문화시설 100분, 레포츠 120분 등)으로 계산합니다.
- **이동 시간은 장소 좌표(TourAPI의 mapx/mapy) 기준 추정**입니다 (직선거리×1.3, 1.2km 미만 도보 / 그 이상 대중교통·차량). 실제 길찾기가 아니에요.
- **점심(12시 무렵)·저녁(18시 무렵) 식당**은 TourAPI 음식점 중 직전 장소에서 가장 가까운 곳을 고르고(취향 유사도 상위 30곳 안), 여행 중 같은 식당이 반복되지 않게 합니다.
- 장소가 적어 비는 시간은 '자유 시간'으로 표시합니다. 예보 범위 밖의 날은 오류 문구 대신 계절 안내(예: "이맘때는 선선한 가을 날씨예요")를 보여줍니다.
- API 실패 사유 같은 **시스템 문구는 답변에 넣지 않고** 화면 왼쪽 "개발자 정보 표시"를 켰을 때만 보입니다. 뉴스는 일정에 넣은 장소와 직접 관련된 것만 "💡 방문 전 확인"으로 보여줘요.
- `성남`, `해운대`처럼 시군구에 해당하는 세부 지역을 말하면 **그 시군구의 장소를 한 번에 전부** 받아옵니다 (`lDongSignguCd`). 이전에는 시도 전체에서 60곳만 받아 걸러서 후보가 1곳만 남는 문제가 있었어요.

```bash
python check_setup.py chat                   #    대화형 플래너 전체 (실제 API + Ollama)
python -m streamlit run chat_app.py          # 4) 채팅 화면

```

## API (Spring Boot / React에서 호출)

| 메서드 | 경로 | 설명 |
|---|---|---|
| POST | `/chat` | 대화로 일정 생성·수정. `session_id`를 계속 보내면 이전 대화를 기억 |
| DELETE | `/chat/{session_id}` | 대화 초기화 |
| POST | `/recommend` | (단발) 조건을 한 번에 넘겨 추천 받기 |
| GET | `/risks?region=부산` | 지역 이슈 뉴스만 조회 (LLM 없음). 저장 일정 알림용 |

```bash
# 처음: session_id 없이 호출 → 응답의 session_id를 이후 요청에 계속 사용
curl -X POST http://localhost:8000/chat -H "Content-Type: application/json" \
  -d '{"message": "이번 주말에 부산 가려고 해요"}'
curl -X POST http://localhost:8000/chat -H "Content-Type: application/json" \
  -d '{"session_id": "<위 응답의 session_id>", "message": "커플이고 바다 보면서 조용히 걷고 싶어요"}'
```

응답 필드: `reply`(마크다운 답변), `stage`(asking/planned), `slots`(파악한 조건), `missing`(더 필요한 정보),
`plan[]`(일자별: date, theme, weather, air, outdoor_ok, items[slot, note, place{name,type,address,indoor,image,mapx,mapy}]),
`conditions[]`, `risks[]`, `caveats[]`, `used_sources[]`.
세션은 서버 메모리에 2시간 보관됩니다(서버를 재시작하면 사라짐).

## 여행지가 안 불러와질 때

`python diagnose_api.py` 를 실행하면 API마다 서버가 돌려준 원문과 판정이 나옵니다.

| 판정 | 의미 |
|---|---|
| `등록되지 않은 인증키` | 키 복사 오류, 또는 활용신청 승인/동기화 전 (수 분~수 시간) |
| `접근 권한이 없습니다` | 그 서비스를 활용신청하지 않았거나 승인 대기 |
| `일일 호출 한도 초과` | 개발계정 호출 한도. 내일 다시 하거나 운영계정 신청 |
| `HTTP 404` | 엔드포인트 URL 오류 (`config.py`의 `ENDPOINTS`) |
| `정상 (0건)` | 키·API는 정상인데 조건에 맞는 데이터가 없음 |
| `시간 초과` | 키 문제가 아니라 제공기관 서버가 느린 것 (에어코리아가 가끔 그래요). 앱은 자동으로 한 번 재시도하고, 그래도 안 되면 그 항목만 빼고 진행합니다 |
| 네이버 `401`/`403` | `[인증 정보]`의 Client ID/Secret이 서로 바뀌었거나 값에 공백/따옴표가 있음, 또는 Application에 `뉴스` API가 등록되지 않음. `python diagnose_api.py naver`가 서버 응답 원문을 보여줍니다 |
| 네이버 `429` | 짧은 시간에 호출이 몰림. 호출 간격 제한과 재시도가 들어 있어 자동으로 완화됩니다 |

Ollama 연결이 안 될 때는 `python diagnose_api.py ollama` 로 `.env`의 주소와 `localhost` 중 어느 쪽이 되는지 확인하세요.
(공유기 환경에서는 PC의 IP가 바뀌는 일이 흔해서, 같은 PC에서 돌린다면 `OLLAMA_BASE_URL=http://localhost:11434` 가 가장 안정적입니다.)

채팅 화면에서는 같은 사유가 답변 아래 **"⚠️ 제약사항 / 한계"** 에 그대로 표시됩니다.

## 알아둘 점

- **날씨는 약 3일, 미세먼지는 오늘~모레**까지만 예보가 제공됩니다. 그 밖의 날짜는 반영하지 못하고 제약사항에 표시됩니다.
- **실내/실외 구분**은 장소 이름과 콘텐츠 유형으로 추정한 값이라 틀릴 수 있습니다.
- **뉴스 이슈**는 최근 7일 기사 기준이라 여행일이 멀수록 현재 상황과 달라질 수 있어요.
- **컨텍스트 길이**: Ollama 기본 컨텍스트가 작으면 프롬프트 앞부분이 잘립니다. `OLLAMA_NUM_CTX`(기본 8192)를 쓰고, 결과가 이상하면 늘려보세요.
- **모델 크기와 PC 사양**: 모델 파일이 RAM+VRAM보다 크면 디스크 스와핑으로 극도로 느려져 일정 생성이 시간 초과(`OLLAMA_TIMEOUT`)로 끝납니다.
  이때도 대화는 이어지고 날씨·미세먼지를 반영한 **기본 일정**이 대신 나옵니다. 더 작은 모델(예: `gemma4:e4b`)로 바꾸면 AI 일정이 나옵니다.
  속도는 `ollama run <모델> --verbose "안녕"` 의 `eval rate`(초당 토큰)로 확인하세요. 일정 응답이 약 700토큰이라 초당 10토큰 이상이면 1~2분, 3토큰이면 4분 가까이 걸립니다.
  후보 수를 줄이는 `CHAT_MAX_CANDIDATES`도 도움이 됩니다.
- **속도(데이터 수집)**: 관광정보·날씨·뉴스·미세먼지를 동시에 호출하고, `GATHER_TIMEOUT_SEC`(기본 40초) 안에 안 끝난 항목은 빼고 진행합니다(늦는 호출은 백그라운드에서 끝나 캐시에 남아 다음엔 빨라져요).
  응답은 `cache/api/`에 저장돼 같은 요청은 다시 부르지 않습니다(관광정보 12시간, 날씨·예보 30분, 뉴스 10분). 지우거나 끄려면 `cache/api` 삭제 또는 `API_CACHE=off`.
  채팅 화면/API 서버는 켜질 때 임베딩 모델을 미리 올려둬서 첫 일정 요청이 모델 로딩을 기다리지 않습니다.
  후보 장소의 임베딩도 `cache/place_embeddings.npz`에 저장해서, 처음 보는 장소만 계산하고 두 번째부터는 취향 문장 하나만 계산합니다.
- **AI의 '생각' 시간**: 일부 모델(예: gemma4)은 답하기 전에 길게 생각합니다. `check_setup.py chat`의 `생각 N자`가 크면 `.env`에 `OLLAMA_THINK=false`를 넣어보세요.
  `python check_setup.py chat`의 `⏱` 줄에 항목별(places/news/weather/air) 시간이 나옵니다.
- **AI 호출 횟수**: 짧은 답("부산 가려고요", "내일부터 2박 3일")과 일정 수정 요청에서는 AI 정보 추출을 건너뛰어서, 일정을 만들 때 AI는 **한 번만** 호출됩니다. (`CHAT_EXTRACT_LLM_MIN_CHARS`)
- **느린 원인 확인**: `python check_setup.py chat`이 데이터 수집 / 후보 검색 / AI 일정 시간과 AI 초당 토큰 수를 보여줍니다. 제약사항에 `AI가 빈 응답`이 나오면 `OLLAMA_THINK=false`를 시도하세요.
- **속도**: 로컬 LLM은 한 번에 하나씩 처리합니다. 일정 생성은 첫 요청이 가장 느리고(데이터 수집 + 임베딩 모델 로드), 수정 요청은 훨씬 빠릅니다.
- **TourAPI는 KorService2** 입니다. 엔드포인트/파라미터는 `config.py`, `collectors/tourism.py`에 있고, 활용신청 후 각 API 상세 문서와 한 번 대조하세요.

## 느린 서버·모델 실패 대비

- 미세먼지(에어코리아)처럼 응답이 느린 API는 기존대로 100건·25초로 요청합니다. 실패하면 최근 저장본(미세먼지 18시간, 날씨·뉴스 6시간, 관광정보 며칠)으로 대신 답하고, 5분(날씨·뉴스는 2분)간 같은 요청을 다시 시도하지 않습니다. 사용자 화면에는 아무 오류도 나오지 않고, 개발 모드(`DEV_MODE=on`)에서만 "저장본 사용" 기록이 보입니다.
- Ollama가 `llama-server startup failed ...`(500)로 모델을 못 띄우는 PC에서는 `.env`에 `OLLAMA_FALLBACK_MODEL=gemma3:4b`처럼 더 작은 텍스트 모델을 적어 두면 500일 때 자동으로 그 모델로 한 번 더 시도합니다. (`ollama pull`로 미리 받아 두세요.) 이 오류는 보통 이미지 처리 부품(mmproj)·그래픽 메모리 때문이라, `OLLAMA_MODEL`을 작은 모델로 바꾸는 것이 가장 확실합니다.
